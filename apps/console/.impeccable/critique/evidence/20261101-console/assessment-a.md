# Assessment A：Forge Console 独立设计评审

方法：独立子代理 `/root/console_design_a`，Operate 模式。目标 `/Users/libo/projects/forge/apps/console/src/main.tsx` 及其共享导航、现有旧版任务路径。未运行或查看 detector、既往 critique、`.design-evidence` 报告或 Assessment B 输出。

## 1. 设计针对性与总体判断

界面的克制是正确的：Forge 是企业操作台，白底、紧凑表格、语义状态和可预测的弹窗比品牌表达更重要。新版 Agent 列表把“线上版本 / 草稿 / 开放 API”分开表达，审批文案解释了暂停机制，已经有产品意识。

但完整体验仍更像“资源数据库的管理入口”，不是围绕“安全构建 Agent → 调试 → 发布；运行 → 审批 → 追溯”的工作台。真正需要理解和决策时，用户要跳去旧版、阅读原始 JSON、抄 ID，再返回列表寻找动作。最大的机会是补齐任务的连续性和决策上下文，而非再换一套视觉语言。没有因为它使用熟悉的 shadcn/表格模式而扣分；对 Operate 界面，这些模式合理。

总体：**23/40，可用但核心任务仍需明显改进**。本次没有发现必须整体推翻视觉体系的依据；优先修复草稿调试路径、Run 阅读与审批追溯。

| 渐进披露 | 未满足 | Agent 详情默认显示全量内部 JSON，基础配置与高级 Spec 混放；Run 同时展开消息、工具和底层事件。 |

**5/8 未充分满足，核心任务认知负担高。** 这并非要求机械把所有清单缩到四项；需要把危险决策与上下文关联起来，并把高级配置放到用户需要时。

>4 选项决策点：构建导航 6 项；旧版有草稿的 Agent 行“试运行 / 新版本 / 发布草稿 / 开放 API / 详情”5 项；凭据资源类型 5 项；账号附加角色 5 项。全局搜索默认也列出整组导航，但它是可搜索的辅助路径，问题程度低于主表行的并列动作。

## 4. 情绪旅程

- **进入控制台：放心。** 清楚的 Agent 表格、草稿和线上版本，不要求先读帮助。
- **想修改/构建：第一个谷底。** 名称不能直接进入工作区，需要“⋯ → 在旧版中查看详情”；详情打开后是 JSON，尚未获得可操作的模型。
- **准备配置：第二个谷底。** Instructions/Spec JSON 承担核心任务，正确配置依赖额外知识；对已有线上 Agent，“新版本”只给“创建并发布”，把试验感变成上线压力。
- **想验证：缺乏确认。** “试运行”输入很简单，但没有标明当前版本/草稿，无法从界面确认正在测什么。
- **查看执行结果：目前应有的峰值被削弱。** Run 有真实消息与事件，但窄消息栏和被挤出的事件内容让成功结果难读。
- **审批：决策压力高。** 未造待办；源码显示可看到脱敏参数和不可撤回提示，但要理解原始任务仍需自己去找 Run。
- **结束：有退出，缺收束。** 关闭/取消可靠，但详情页没有把“当前测试的版本、结果、下一步是否可发布”收在同一处。峰终规则上，最值得打磨的是验证完成后的确定感。

## 5. 三点优势

1. **新版列表的状态是可读信息。** “线上 v1.0.0”和“草稿 v1.0.0”用文字区分，不只靠颜色；API 开放状态独立，方便运维扫描。见 `a/agents-1440.png`。
2. **对跨版去向保持诚实。** “去旧版新建”、菜单里的“在旧版中查看详情”、搜索结果的“旧版”标签能解释去向；没有把未迁移能力伪装成新版已交付。实际触达成本仍需改善，但文案方向正确。
3. **退出与短屏处理有基础。** 1280×560 下长创建表单的操作区仍可达；实测 Esc 关闭，修改凭据作用域后有未保存确认。新版 1280×800 导航与主要表格完整，短屏允许导航滚动。见 `a/agent-create-short.png`、`a/agents-1280.png`、`a/agents-short.png`。

## 6. 最值得先改的五项

### A1 [P1] “配置新版本”默认就发布，草稿→调试→发布的安全路径没有在 UI 成立

**证据性质：真实表单 + 已核实调用链；没有提交。** 管理员的新建 Agent 与“新版本”表单都只有“创建并发布”；试运行只有输入文本，没有版本选择/版本说明。旧版新版本提交固定 `publish: true`；试运行请求不传 `versionId`，API 默认取已发布版本。后端已经接受显式 versionId，UI 可复用现有能力。

**用户影响：** 编辑线上 Agent 时，用户不能先把新配置作为草稿保存并测试；要么冒险发布，要么绕开 UI。即使已有草稿，试运行也不能明确选择它。这是操作安全和信心问题。

**改法：** 新建/新版本以“保存草稿”为主动作；在同一 Agent 上明确展示“当前草稿 / 已发布版本”，允许选择草稿试运行；发布独立显示差异、目标版本和影响确认。优先把后端已经支持的版本选择接入表单，不必先重做整个编辑器。

**源码：** `apps/console/public/app.js:1062–1102`、`:1286–1302`；`apps/api/src/routes/admin/agents.ts:143–154`。**截图：** `a/agent-create-1280.png`、`a/agent-version-1280.png`、`a/agent-debug-1280.png`。**建议命令：** `$impeccable shape` / `$impeccable harden`。

### A2 [P1] Run 详情的两列布局在正常桌面窗口把主要消息挤成窄条

**证据性质：真实已有 Run，1440×900 实际截图。** 680px 弹窗内仍强制消息/诊断两列，右侧事件行含 42px + 150px 固定列及 JSON 最小宽度；示例最终回答在左侧被压到很窄、频繁断行，事件块又向右溢出正文可视区。不是手机问题。

**用户影响：** 运行“成功”的核心产物最难阅读，排障时还需在弹窗正文及事件块中找横滚；用户很难快速确认结果是否正确。

**改法：** 默认弹窗把消息作为完整宽度的主内容，工具/事件用 Tab 或可折叠诊断区；如保留两列，按弹窗容器宽度决定断点，列使用 `minmax(0, …)`，子项允许缩小，JSON 在自身范围换行/横滚。事件字段不应反过来决定消息宽度。

**源码：** `apps/console/public/styles.css:128`、`:146–149`；`apps/console/public/app.js:1483–1493`。**截图：** `a/run-detail-1440.png`（主要证据）、`a/runs-1280.png`。**建议命令：** `$impeccable layout`。

### A3 [P1] 新版审批不能直接追溯到这条 Run，决策上下文被拆开

**证据性质：源码确认；实时页仅有空态，未伪造待办或打开决定框。** 审批行“在旧版中查看 Run”的 href 固定 `/#runs`，没有 run_id；Run 列表只加载最近 100 条，且没有搜索/筛选。批准确认只显示 Agent/工具名称和 args_preview，没有原始任务与风险触发解释。

**用户影响：** 审批人需要自己抄 ID 并在另一套界面找执行记录。高风险批准的前提本应是理解这次调用；目前最显眼的是批准，证据反而需要跨屏拼接。若目标 Run 不在最近 100 条，列表路径更弱。

**改法：** “查看 Run”带当前 run_id，直接打开该执行及对应工具调用；审批详情先展示原始请求摘要、工具及脱敏参数、风险/中断原因和剩余时限，再给批准/驳回。保留现有不可撤回和“可能已执行过”的提示。可以先实现旧版 Run 深链接，减少一次无上下文的列表跳转。

**源码：** `apps/console/src/features/approvals/index.tsx:174–198`、`:222–245`；`apps/console/public/app.js:629–637`。**截图：** `a/approvals-1440.png` 仅证明实际空态；`a/runs-1280.png` 证明列表形态，**不能当作待审批行视觉验收**。**建议命令：** `$impeccable shape` / `$impeccable clarify`。

### A4 [P2] 详情和基础配置把内部表示直接交给用户，识别成本高

**证据性质：真实 Agent 详情、创建、凭据表单。** Agent 详情把完整响应 JSON 当正文；创建/新版本要求用户编辑 Spec JSON；凭据选择指定资源后要手填“组织 / 资源 ID”，资源类型是 `llm_provider/mcp_server/tool_source/api_app` 等内部名。详情的开头先出现 id/revision/ownerOrgUnitId，而不是用户要确认的模型、工具和预算。

**用户影响：** 构建者要记住 schema、资源 key 和 ID；管理员配置凭据时离开表单找对象，增加配错作用域的机会。熟悉技术不等于值得把每次操作都变成读 JSON。

**改法：** Agent 详情先展示模型、Instructions、工具/Skill、预算、版本和 API 开放的可读摘要；JSON 放“高级/原始配置”。基础模型/工具用现有目录选择器；凭据资源按名称/Key 搜索选择并回显 ID，组织与资源使用分别明确的标签。允许保留高级 JSON 路径，避免一次重做全部配置能力。

**源码：** `apps/console/public/app.js:1064–1071`、`:1093–1097`、`:1111–1131`、`:1336–1340`。**截图：** `a/agent-detail-1440.png`、`a/agent-create-1280.png`、`a/secret-resource-1280.png`。**建议命令：** `$impeccable clarify` / `$impeccable onboard`。

### A5 [P2] 新版 Agent 列表把“进入工作”藏在更多菜单里

**证据性质：真实列表与菜单 + 源码。** Agent 名称是普通 div，不能打开详情；列表没有“配置/调试”主入口。可见动作集中在发布/API，查看详情需打开更多菜单，再进入旧版 JSON 弹窗。

**用户影响：** 想检查/修改/测试 Agent 的高频用户先学习菜单和两套界面；对无待发布草稿的行，唯一显眼的可操作内容是 API 开关。列表很整洁，但任务入口的层级倒置了。

**改法：** 名称变为详情链接，每行提供“配置/调试”主入口；发布留在草稿状态旁或菜单里，保留危险动作确认；迁移期可继续带明确旧版标签，但入口应直达该对象，不要求用户先识别“⋯”。

**源码：** `apps/console/src/features/agents/index.tsx:127–135`、`:165–198`。**截图：** `a/agents-1440.png`、`a/agents-1280.png`；菜单已实际展开观察，未另存菜单截图。**建议命令：** `$impeccable distill` / `$impeccable shape`。

## 7. Persona 实测/推演

- **Alex，熟练构建者：** 从新版列表检查 demo-agent，先打开 ⋯ 才能找到详情；详情是 JSON，要改配置需关掉再找“新版本”；新版本只能创建并发布。⌘K 快捷导航好用，但旧版 Run 仍没有按 Agent/状态/ID 快速定位。障碍是动作连续性，不是缺少花哨效率功能。

## 8. 较小观察与启发问题

- 旧版 Agent 在1280×800下，版本“未发布”和 API“未开放”会被挤成两行，操作列却保留最多5个并列按钮。先收拢次要动作，比单纯缩字号更有效。见 `a/legacy-agents-1280.png`。
- 新旧版相同状态分别显示“启用”和 `active`、运行状态仍为 `succeeded`；可复用中文状态词，减少跨版切换的翻译负担。
- 账号创建表单已经用中文名称、可选部门和附加角色分组，说明不必把每个管理对象都表达为裸 ID 或 JSON。见 `a/account-create-1280.png`。
- 当前源码和真实页面新增 Job 管理；实际只读看过空列表与创建弹窗，未保存，也没有据此宣称 Job 整体完成。其空态缺少任务用途说明，可后续与 Agent/定时任务的边界一起说明，暂不升为本次最高优先级。

供 parent 最后选用的问题：

1. 能否把“草稿配置、测试的版本、发布条件”放在同一个 Agent 工作区，让每一步都能确认自己改了什么、测了什么？
2. 审批人的第一屏若先回答“这次请求要做什么、为什么需我确认”，是否比先看一排批准按钮更合适？

# Forge 当前控制台界面体验评审

评审日期：2026-11-01。模式：Operate（完成任务的操作台）。稳定目标：`src/main.tsx`，覆盖新版共享导航、Agent/审批，以及旧版配置与运行路径。使用本轮最新前端构建和既有本地 forge_test 数据；Job 正在并发开发，只记录取证时点，不作整体交付判断。

当前控制台有清楚的列表和状态基础。建议沿用现有视觉，优先补齐“草稿 → 调试 → 发布”和“运行 → 审批 → 追溯”的连续性。整体启发式评分为 **23/40：可用，核心任务仍需改进**；这不是后端质量分或生产验收结果。

## 设计针对性与总体印象

白底、紧凑表格、语义状态和熟悉的后台模式适合 Forge。新版把线上版本、草稿和开放 API 分开表达，具备产品针对性。主要弱点集中在深入操作以后：进入旧版、读原始 JSON、寻找 ID 和对象，再返回列表。优先让用户明确“正在修改哪个版本、测试哪个版本、这次执行发生了什么”。

## 已经有效的设计

- 新版线上版本、草稿和 API 开放状态分别呈现，文字与颜色共同表达状态，便于扫描。
- “去旧版新建”“在旧版中查看详情”诚实标明去向；迁移期文案值得保留。
- 取消、Esc、未保存提示和短屏表单滚动已有基础，1280×560 下长表单的操作区仍可达。

## 五项优先建议

### 1. [P1] 补齐草稿调试与发布路径

管理员“新版本”表单只有“创建并发布”，提交固定 `publish: true`；试运行不展示或选择版本，默认使用已发布版本。用户无法在界面中确认“先保存、测草稿、再上线”。

建议先接入后端已有的版本选择能力：保存草稿为独立动作，调试明确选择和展示版本，发布单独确认目标版本与影响。无需先重做整个编辑器。建议命令：`$impeccable shape`。

证据：真实表单与调用链，未提交；[创建新版本截图](evidence/20261101-console/agent-version-1280.png)。源码：`apps/console/public/app.js:1062`、`:1093`、`:1286`；`apps/api/src/routes/admin/agents.ts:143`。

### 2. [P1] 让 Run 结果成为详情主内容

1440×900 正常桌面下，680px 弹窗仍按两列展示，右侧事件区域的最小宽度把左侧消息挤成窄栏。成功结果频繁断行，事件正文也溢出可视区域，直接影响阅读与排障。

建议默认完整宽度显示消息，把工具和事件放入 Tab 或折叠区；保留分栏时按弹窗宽度而非屏幕宽度决定布局，限制诊断区域自身的换行和横滚。建议命令：`$impeccable layout`。

证据：[1440×900 Run 详情截图](evidence/20261101-console/run-detail-1440.png)。源码：`apps/console/public/styles.css:128`、`:146`；`apps/console/public/app.js:1483`。

### 3. [P1] 审批直接关联到具体 Run

当前“在旧版中查看 Run”的链接固定为 `/#runs`，没有带目标 Run；运行列表也没有搜索。审批人需要跨页自行寻找执行记录。

建议首先提供具体 Run 的直达链接，再把原始请求摘要、工具与脱敏参数、风险或中断原因、剩余时限放在审批决定之前。建议命令：`$impeccable harden`。

此项为**源码确认**；本地实际待审批数为零，未伪造待办或执行批准/驳回。源码：`apps/console/src/features/approvals/index.tsx:196`、`:222`；`apps/console/public/app.js:629`。

### 4. [P2] 用可读摘要和对象选择减少 JSON、ID 记忆

Agent 详情默认是完整响应 JSON；基础配置和高级 Spec 混在一起；凭据指定作用域要求手填组织/资源 ID。构建者需要记 schema，管理员需要跨页找对象。

建议详情先显示模型、指令、工具/Skill、预算和版本；原始 JSON 放高级区。作用域按名称/Key 搜索选择并回显 ID，内部资源类型配中文名称。建议命令：`$impeccable clarify`，涉及表单结构时先 `$impeccable shape`。

证据：[Agent 详情](evidence/20261101-console/agent-detail-1440.png)、[凭据作用域表单](evidence/20261101-console/secret-resource-1280.png)。源码：`apps/console/public/app.js:1065`、`:1112`、`:1336`。

### 5. [P2] 把进入 Agent 的入口放回名称和行主操作

新版 Agent 名称不能点击；查看详情、配置和试运行要先打开“⋯”，显眼的行操作主要是发布与 API 开关。高频工作入口不够直接。

建议名称可进入该 Agent，每行保留一个“配置/调试”入口，次要动作继续收在菜单；迁移期保留旧版提示并直达对象。建议命令：`$impeccable polish`。

证据：[新版 Agent 列表](evidence/20261101-console/agents-1440.png)。源码：`apps/console/src/features/agents/index.tsx:127`、`:165`。

## 认知负担与角色推演

八项检查中，单一焦点、相关信息分组、总体视觉层级较好；分块、单次决策、选择数量、上下文记忆、渐进披露共五项需要改善。具体表现为旧版 Agent 一行最多五个动作、基础设置混在 Spec 中、审批与凭据跨屏找对象。导航“构建”组有六项，但不建议机械压缩到四项；应优先降低关键决策的负担。

体验路径：进入列表清楚 → 配置时跨版且依赖 JSON → 新版本直接发布带来压力 → 调试版本不确定 → 结果阅读又被诊断内容挤压。最值得提升的是验证完成后的确定感。

- **Alex，熟练构建者**：检查、改版本、调试需多次切换菜单和旧版；现有 ⌘K 有效，应保留。
- **Jordan，首次配置的管理员**：Spec、工具引用和资源 ID 缺少就地解释，难以确认配置对象。
- **Sam，键盘或低视力操作员**：Esc 和退出基础可用；Run 窄栏与原始 JSON 放大阅读负担。未以真实辅助技术验证全流程。

## 次要观察

- 1280×800 下，新版最后一个 SSO / Connector 导航需要滚动才能看到；增加 Job 入口后应重新核算侧栏高度，仍保留滚动兜底。
- 旧版 1280px Agent 表格把“未发布”“未开放”挤成两行，而操作列保留多个按钮。先调整列宽与次要动作收纳，避免缩小字号。
- 新旧版的“启用 / active”“成功 / succeeded”宜统一为用户可读的中文状态。

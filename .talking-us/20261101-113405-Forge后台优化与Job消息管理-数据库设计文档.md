# Forge Job 与消息管理数据库设计

版本：1.0　日期：2026-11-01　状态：**READY FOR IMPLEMENTATION（本增量数据规格）**

权威需求：[详细需求v1.0](20261101-113405-Forge后台优化与Job消息管理-详细需求文档.md)。组合使用：[开发设计](20261101-113405-Forge后台优化与Job消息管理-开发设计文档.md)、[接口设计](20261101-113405-Forge后台优化与Job消息管理-接口文档.md)。本文是拟实施规格，不是已执行迁移或实测数据库快照；当前仅按仓库Schema/Drizzle及001–012迁移代码核对，未连接业务/生产数据库。

## 1. 基线与单一模型

- 实际存在 `schedules.agent_id NOT NULL`、`api_apps.webhook_url/webhook_secret_id`、`webhook_deliveries`、`files.storage_path`、`settings.revision/value_json`。`artifacts/outbox_events/run_policy_snapshots/eval_*` 只有目标设计，不当成已建表。
- 沿用 [MySQL设计](../docs/04-data/mysql-design.md)和[执行环境数据设计](2026-10-31-forge-data-design.md)的同名目标表。**不再建立webhook_endpoints**：其配置职责由message_channels及版本承担；历史webhook_deliveries只作兼容镜像。`messages`继续是Agent会话消息，外部通知使用message_deliveries，不混表。
- 所有SQL在store；新表同步Drizzle、forward-only迁移、空库/升级/重跑验证。迁移逻辑名见第8节，编号在实施时接续实际迁移记录，本文不抢占013或已有Drizzle编号。
- 新实体使用完整ULID，存 `CHAR(26) CHARACTER SET ascii COLLATE ascii_bin`。旧26位前缀ID保留；现有core/ids已经同时接受两种格式，不重写旧主键或放宽任意字符串。新ID经core统一生成，不把截短前缀ID当完整ULID。

## 2. 字段约定与公共列

所有表显式 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`。以下缩写为DDL规格，**不是省略待定字段**：

| 缩写 | 完整类型/规则 |
| --- | --- |
| I | CHAR(26) CHARACTER SET ascii COLLATE ascii_bin；ID/外键允许现有合法前缀ID |
| H | CHAR(64) CHARACTER SET ascii COLLATE ascii_bin；SHA256十六进制小写 |
| S(n) | VARCHAR(n) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin；标识/枚举区分大小写 |
| T(n) | VARCHAR(n)；正文/name使用默认utf8mb4排序，但Key唯一显式ascii_bin |
| U / B / M / D | INT UNSIGNED / BIGINT UNSIGNED / DECIMAL(12,6) / DATETIME(3) UTC |
| J | JSON，写入前由contracts验证，敏感正文受权限约束；原始Token/URL密钥不得进入普通J列 |
| C（配置公共列） | id I PK；key VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL UNIQUE；name T(128) NOT NULL；description T(1024) NOT NULL DEFAULT ''；owner_org_unit_id I NULL；created_by I NULL；revision U NOT NULL DEFAULT 1；status S(16) NOT NULL DEFAULT 'disabled' CHECK active/disabled/deleted；created_at D NOT NULL DEFAULT CURRENT_TIMESTAMP(3)；updated_at D NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) |
| A（记录公共列） | id I PK；created_at D NOT NULL DEFAULT CURRENT_TIMESTAMP(3)。只有下表明确列出的记录有updated_at/state_revision；日志/事件不软删除 |

下列字段未写NULL即NOT NULL；默认值只按显式声明，不能以空串代替NULL。C用于job_definitions、message_channels、message_templates、message_rules、eval_datasets；其它表逐项列全。配置父记录软删保留Key，发布版本不可变，删除引用使用RESTRICT。运行/日志关联的外键按下表说明；事件不建级联外键，以便保留事实与分批清理。

锁顺序固定：Job定义→执行→按ID排序的步骤/attempt→按hash排序的资源锁→费用许可→事件/outbox；人工动作亦先锁执行。外部调用不持有SQL事务。资源锁只有在未发出或已证明结束/目标对账确认时释放；未知写入和取消未确认不释放。资源锁与执行租约分开，防止租约过期导致两个浏览器同时写同一站点。

## 4. 消息模型

### 4.1 配置与不可变版本（新增）

| 表 | 字段 | 约束/索引 |
| --- | --- | --- |
| message_channels | C；type S(16)（webhook/wecom）；published_version_id I NULL；next_version U DEFAULT 1；legacy_app_id I NULL；credential_owner_type S(24)；credential_owner_id I；dispatch_epoch B DEFAULT 1 | UNIQUE(legacy_app_id)允许多个NULL；FK legacy_app RESTRICT；idx_message_channels_org(owner_org_unit_id,status,id)。新渠道owner=message_channel/自身ID；兼容渠道owner=api_app/legacy_app_id且组织严格一致，不允许客户端自填委托身份 |

| message_templates | C；draft_json J；published_version_id I NULL；next_version U DEFAULT 1 | idx_message_templates_org(owner_org_unit_id,status,id) |
| message_template_versions | A；template_id I；version U；format S(24)；content TEXT；variables_json J；content_hash H；created_by I NULL | FK template RESTRICT；UNIQUE(template_id,version)；format=wecom_text，变量白名单。业务Webhook固定事件Schema，不写入自由模板 |
| message_rules | C；event_type S(64)；scope_type S(16)；scope_id I NULL；channel_id I；template_version_id I NULL；include_nested_runs TINYINT(1) DEFAULT 0 | FK channel/templateVersion RESTRICT；scope=job/agent/api_app/org/global；仅global可NULL，平台有权主体方可global；idx_message_rules_match(event_type,status,owner_org_unit_id,scope_type,scope_id)。每规则一个事件＋渠道；多个事件/渠道建立明确的多条规则，无隐式任意路由脚本 |

规则版本以C.revision标识；事件产生事务复制获准匹配结果（rule_id/revision/channelVersion/templateVersion和范围）到outbox.targets_json，无须再造通用规则版本表。删除/停用渠道的实时状态仍发送前检查。重叠规则对同event/channel只产生一个逻辑消息，按scope精确度job/agent/api_app→org→global、再规则ID排序确定内容；保存时同scope/event/channel冲突，来源列表入记录。

endpoint Secret是配置快照：输入value或获准secretId时，由服务端在同一事务创建当前渠道/精确legacyApp作用域的新URL快照（未变地址可复用原快照）。`resource_references.binding_key=endpoint-version:{versionId}`标识不可变值；普通Secret值轮换对此返回409并引导修改渠道地址，新版本创建新Secret，不让旧投递因同一Secret引用轮换而改投。主密钥重包裹允许且不改变明文；Secret停用/撤销仍即时阻断发送。signing/header凭据继续使用其当前有效版本，不与URL快照的不可变语义混淆。

## 7. 一致性、保留与DDL验证

1. 以**执行/渠道父行先行锁定**序列化受理、控制、重发和配置变更；legacy渠道配置先App→channel，发送channel→delivery，不反向申请App写锁。事件、审计、outbox使用同一PoolConnection。当前db.ts只设置时区，隔离级别未实测；新事务在begin前明确READ COMMITTED。现有createQueuedRun/finalize不是完整原子保证，不能外层套transaction而内部仍用pool.execute。
2. 状态CAS检查 `state_revision/generation/fence_token`；所有attempt子表写入先验证执行/投递父锁。SQL返回0行即丢失拥有权，停止后续调用，不能当普通工具失败继续。
3. FK为RESTRICT，无事件级联。Job定义/渠道删除先查版本/执行/规则/待发引用；组织移动不改历史执行归属，下载/SSE仍与当前有效策略取交集。
4. 正文保留按需求L07；活动、未知、持有人未确认停止、人工待办未闭合和业务交付未闭合记录不清。清理先标待清理/持引用检查→删对象→清正文→保留去重摘要；对象删除未知先查对象状态，不清唯一副本。
5. DDL需显式COMMENT（按本字典含义）、CHECK枚举/非负/状态组合、索引列顺序、字符集与外键。CHECK由MySQL 8.0.30+实际执行；实现时不依靠Drizzle应用校验替代数据库约束。
6. 代表查询：执行列表WHERE组织/主体＋created_at/id游标；明细WHEREexecution_id/status；消息WHERE组织/渠道/时间；待处理WHEREstatus/next_attempt_at；所有list/find/export在SQL内带AccessContext。实施后用真实MySQL EXPLAIN确认索引，不把本索引设计称实测性能。

## 8. 迁移、回填与回退

逻辑批次：`job_core_expand`→`message_management_expand`→`evidence_artifact_quality_expand`（按消费者实施）；每批迁移写Schema、Drizzle与幂等结构断言。结构迁移不连第三方、不发消息、不自动激活Job。

- 从空库：先现有001–012及适用E1/E3基础，再父表→版本→执行/步骤→attempt→记录/outbox→消息→质量/评测。自引用/循环指针先无FK建父子，数据写入服务校验归属；需要FK的非循环边最后添加并校验。
- 升级：先备份、人工发布审批；每个ALTER前查information_schema，检查已有列完整类型/默认/索引，不仅IF NOT EXISTS。大表nullable列先扩、索引另建并评估锁；DDL自动提交，失败不能假装事务已回滚。
- 回填用独立受控维护命令；按主键游标每批100条，单批事务保存mapping与settings进度。新ID首次生成并持久映射后复用；同源配置UNIQUE(legacy_app_id)，同源投递沿用旧ID，重跑不重复插入。
- 旧计划一对一创建Agent型Job与版本，保存schedule→job映射，保留参数、服务账号、时区、版本策略和skip。没有有效服务账号的legacy计划保留停用待指定，不伪造服务身份；历史非skip记录显式检查后启用。
- 旧Webhook一对一建channel/rule。平台/组织Secret沿原范围；resource=api_app的Secret继续由精确绑定的api_app消费者解析，不改成平台Secret，也不任意克隆/改写其AAD。URL迁入endpoint Secret，兼容镜像只为过渡版使用。
- 投递复制eventId/type、次数、时间及状态；待发/重试body用原`JSON.stringify(maskArgsDeep(parseLegacy(payload_json)))`序列化器生成并冻结UTF-8字节，通过向量核对。旧表没有历史请求原始字节，不声称还原每次旧签名输入；历史无attempt细节只写legacy_attempts。原pending下一次attempt从legacy_attempts+1开始，受剩余预算约束；原delivered不重新排队。
- 每批对账数量、源→目标唯一映射、payload hash、event/delivery ID、组织/消费者/凭据引用；不能输出地址与密钥。任何冲突或无法证明在途请求结束立即停在quiescing，交核查，不强行切换。
- 只读切换窗口内，对每App/UTC自然日以旧直接Run数量初始化quota_usage_counters一次，记录cutoff与基线hash；新Job/Run受理暂停。恢复后统一入口原子加计，嵌套Run不计第二次；不得把旧COUNT与已包含它的counter再次相加。
- 混合版本仅允许“已懂新字段的兼容版”与新版本组合。正式切换先停触发/派发、排空并确认所有旧派发进程停止；未知在途记录挂起。详见开发设计切换算法。
- **代码回退到兼容版**，保留新Schema/映射和新执行记录；不直接回退不认识Job/渠道的0.1.0二进制。Schema不逆向删；需要恢复备份时必须同时对账外部已发生副作用和消息去重，不能只恢复MySQL就重发。

> **每一格写正确行为**（状态码 + 错误码 + 文案）；代码现状不符的写进「备注」并标**已知缺陷**，执行如实记 fail。`n/a` = 该路由无此类判定。
> **执行约定**：
> 1. admin 写请求一律带本会话 `X-CSRF-Token`（I-CSRF-*）；逐角色期望见 I-RBAC-10（权限列 × inventory §3）。
> 2. **测写接口的 401 / 403 / CSRF 时必须带合法 body（如 `{}`，或不带 Content-Type）**：请求体在 CSRF 之前解析（`apps/api/src/plugins/csrf.ts:7` 挂在 preHandler，解析在它之前），坏 JSON / 超 2MB / Content-Type 不支持 / 空 JSON 体会先失败，走不到 401 / 403（见 I-CSRF-06，已知缺陷 K-09）。顺序：① 解析 body → ② CSRF（仅有效会话时）→ ③ `admin()` 401 / 权限 403 → ④ handler 内 404 / 400。
> 3. 「审计」列即 I-AUD-01 的判定依据：成功写操作后 `GET /admin/api/audit` 的 action 必须与本列一致；被拒绝（401/403/404/400/409）的请求不写审计。
> 4. 「数据范围」列口径：R-run / R-sched / R-sa 一律「本部门 + 所有子部门」（R-sched、R-sa 现状精确等于，已知缺陷）；users / audit / dashboard 按部门过滤、apps 等全局可读为架构师建议，标【待 Cursor Jackson 拍板】。
